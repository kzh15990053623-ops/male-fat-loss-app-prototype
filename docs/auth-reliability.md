# 认证链路可靠性方案

## 第一性原理

用户点击“注册”时，真正需要成立的不是“本地页面能打开”，而是以下四个条件同时成立：

1. 配置合法：Project URL 与 Publishable key 存在且格式有效。
2. 项目可达：域名可解析，TLS 与网络连接正常。
3. Auth 就绪：Supabase Auth 设置接口能接受当前 key 并正常响应。
4. 注册允许：项目没有关闭新用户注册。

因此，`/api/health` 只回答本地进程是否活着；`/api/readiness` 才回答认证依赖是否可用。两者不能互相替代。

## 运行时约束

- 登录页显示前发起 `GET /api/readiness`，不创建用户、不写数据库、不发送邮件。
- readiness 结果缓存 30 秒，避免每次渲染都访问外部服务；用户点击“重新检查”时使用 `?force=1` 绕过缓存。
- 未就绪时禁用邮箱、密码和提交按钮，并展示稳定错误码与可操作说明。
- 注册接口在校验本地输入后再次检查 readiness，防止前端状态过期或请求绕过 UI。
- 所有 Supabase 请求都有明确超时，网络错误被归类为 DNS、超时、TLS、密钥、上游服务和限流，不向用户暴露原始 `fetch failed`。

## 验证边界

- `npm run check` 使用注入的假响应验证所有分支，结果可重复且不会触碰真实账号。
- `npm run test:e2e` 验证页面状态、禁用逻辑、重试恢复和模拟登录闭环；它不证明真实 Supabase 项目可用。
- `npm run check:supabase` 使用当前 `.env` 做真实、只读的 Auth readiness 检查；它证明可达与注册开关，但仍不创建测试用户。
- 真正的注册邮件、邮箱确认和跨设备会话只能在专用测试项目与可清理测试账号流程就绪后加入外部集成测试。

## 本机开发兜底

第三方账号权限无法由应用代码代办，因此开发环境允许用户显式切换为本机账号。该模式与 Supabase 使用相同的前端认证和状态接口，但服务端分流到独立本机适配器：

- 邮箱只用于区分本机档案，密码使用 scrypt 加盐哈希，不保存明文。
- access token 只存在于服务进程内存，refresh token 只以 SHA-256 哈希形式落盘并在刷新时轮换。
- 健康状态按用户 ID 隔离写入 `data/local-auth.json`，静态服务器拒绝访问整个 `data` 目录。
- 页面明确标注“本机账号”，同步状态显示“本机账号已保存”，不使用“云端已同步”措辞。
- 托管和生产环境默认关闭；它是开发可用性兜底，不替代正式 Supabase 多设备同步。
