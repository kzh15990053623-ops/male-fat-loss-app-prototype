## 3. 设计规范：墨玉东方风

### 3.1 设计理念

以东方美学中的 **「静气」** 为核心：

- **宣纸底** — 米白偏暖的纸感底色，而非纯白，避免刺眼与廉价感
- **墨黑字** — 用墨色（#1F1F1F）而非纯黑（#000），字重与留白共同营造呼吸感
- **原木辅** — 低饱和木质色作为分隔与辅助，替代灰色系
- **朱砂点** — 朱砂红作为**唯一强调色**，克制使用（印章、激活态、关键进度）

**避免「AI 味」的具体手法**：

1. 不使用饱和渐变、发光阴影、大圆角（非全圆角，`8/12/16px` 克制取值）
2. 极淡阴影（透明度 4%–8%），模拟宣纸透光而非悬浮卡片
3. 发丝级描边（8%–15% 墨色），替代粗边框
4. 叠加极低透明度噪点纹理，模拟纸张肌理
5. 标题用衬线体（宋体系），正文保持黑体，形成「手写标题 + 印刷正文」的层次
6. 动效放缓、幅度小，避免弹跳感

### 3.3 关键变量接管（重要）

原 `tokens.css` 中的品牌色是**绿色系**，旧组件大量直接引用旧变量名。
新主题**不重写旧文件**，而是在 `:root` 中重新赋值同名变量，让未逐条改造的组件自动继承新配色：

```css
/* 接管旧变量：未逐条改造的组件自动继承新配色 */
--green: #1f1f1f;        /* 原品牌绿 → 墨色（最关键的一条） */
--muted: #6b6b6b;
--muted-2: #8a8a8a;
--white: #ffffff;
--switch-track-off: #e8e0d5;
--focus-ring-soft: rgba(31, 31, 31, 0.1);
```

同时覆盖了旧变量中带绿色倾向的值：

- `--ink-3`：`#496059`（偏绿灰） → `#4a4a4a`（中性灰）
- `--signal`：`#367e66` → `#2d5a3d`
- `--line`：`rgba(34,53,47,...)`（偏绿） → `rgba(31,31,31,...)`
- `--focus-ring-soft`：`rgba(22,167,125,...)`（薄荷绿） → `rgba(31,31,31,...)`

### 3.4 主题文件章节结构

主题仍在 styles.css 的最后导入，按变量、基础与标题、卡片、按钮与导航、图表、输入与开关、弹层、页面组件、旧色覆盖、响应式、减少动效的顺序维护。以注释和选择器定位，避免依赖固定行号。

- 新样式优先放在主题文件；旧文件的功能布局保持原样。
- 图表渐变颜色由 CSS 的 .line-chart stop 接管；渲染层保留每张图自己的 fill 引用，不能统一改成 #chartFill。
- 文字与白字印章使用深朱砂；装饰进度、点缀使用普通朱砂；成功状态保留低饱和墨玉绿。

## 5. 踩坑记录：为什么"改了但看起来没变"（★ 最重要）

用户反馈"点进来首页风格还是原来的"。**这是三个问题叠加导致的**，任何一个单独存在都会让改造看起来无效。

### 5.1 根因一：只定义新变量，没有接管旧变量

**现象**：背景变成了宣纸米色，但**按钮、图标、激活态仍然是绿色**，整体观感仍是旧主题。

**原因**：原 `components.css` / `pages.css` 中的组件大量直接引用 `tokens.css` 的旧变量，例如：

```css
/* 旧代码（未改动） */
.primary-button { background: var(--green); }
```

新主题只定义了 `--paper`、`--ink`、`--cinnabar` 等**新变量名**，
但 `--green` 仍指向 `tokens.css` 里的品牌绿 → 组件自然还是绿的。

**修复**：在 `:root` 中重新赋值旧变量名，让存量组件自动继承：

```css
--green: #1f1f1f;   /* 原品牌绿 → 墨色 */
--muted: #6b6b6b;
--muted-2: #8a8a8a;
```

**教训**：改造主题时，**先列出旧 tokens 的变量清单并逐个决定去向**，不要只写新变量。
`tokens.css` 是唯一事实来源，改造前必须完整通读。

### 5.2 根因二：Service Worker + 版本戳缓存未失效

**现象**：即使 CSS 已改对，浏览器仍加载旧样式。

**排查范围**：项目是 PWA，`sw.js` 预缓存整个 app shell。当前源码对页面与静态资源采用网络优先、失败后回退缓存，因此“没有升级缓存就永远看不到新样式”并不准确；必须区分在线响应、离线缓存和实际发布版本。

- 改版初期的旧缓存代号为 `v22`，入口版本为 `20260926-1`。
- 当前发布流程仍需递增版本与缓存代号，保证新应用壳预缓存与离线回退一致；最新版见第 7 节。

**修复**：

1. 运行 `npm run bump:version`（脚本会自动同步 `index.html` 的两处 `?v=`、
   `sw.js` 的 `APP_SHELL` 版本戳，并递增 `CACHE_NAME`）
2. 新文件必须加入 `sw.js` 的 `APP_SHELL` 清单，否则离线时该文件不可用
3. 在线确认响应资源和版本戳，检查新 SW 激活及缓存内容，然后断网重开验证。强制刷新只作为调试辅助，不作为 SW 更新成功的证据。

**教训**：**任何前端资源改动后都要 `npm run bump:version`**，这是本项目的强制流程。
`validate-version-sync.mjs` 会校验三处版本戳一致，不一致直接门禁失败。

### 5.3 根因三：旧文件里的硬编码颜色

**现象**：变量已接管，但仍有零星绿色/深蓝残留。

**原因**：旧 CSS 中有**不经变量、直接写死**的颜色值。扫描结果：

```bash
# 扫描命令（可复用于后续排查）
Select-String -Path "src\styles\base.css","src\styles\components.css","src\styles\pages.css" `
  -Pattern "rgba\([^)]*\)|#[0-9a-fA-F]{3,6}" -AllMatches |
  ForEach-Object { $_.Matches.Value } | Group-Object | Sort-Object Count -Descending
```

发现的主要残留（绿/深蓝族）：

| 残留值 | 位置 | 处理 |
|---|---|---|
| `rgba(22, 167, 125, ...)` ×9 | 焦点框、周计划今日、进度条光晕、服务状态 | 主题文件 L604 段接管 |
| `rgba(11, 113, 91, 0.2)` | 骨架屏品牌条 | → `--wood-light` |
| `rgba(7, 82, 66, 0.2)` | 开关选中阴影 | 主题文件 L657 段接管 |
| `rgba(16, 42, 58, ...)` ×9 | 旧墨蓝：Toast、进度条、开关、迷你柱状图 | 主题文件 L604/L657 段接管 |
| `#9be7d0` / `#8be0c7` | 薄荷绿：营养结果、眉题 | 主题文件 L604 段接管 |
| `#075e4d` | 完成按钮 hover | → `--ink-2` |
| `#e9ebe6` / `#98a1a2` | 旧底色/占位符 | 主题文件接管 |

**处理策略**：不逐个改旧文件，而是在主题文件末尾新增两个章节统一覆盖：

## 6. 项目硬性约束（改代码前必读）

这些是项目既有约定，**违反会直接导致门禁失败或线上事故**：

### 6.1 CSP 禁止内联样式

`server.mjs` 下发的 CSP 中 `style-src` **没有 `'unsafe-inline'`**。

> ❌ 禁止在渲染层输出 `style="..."` 属性
> ✅ 所有动态样式必须通过 class + CSS 变量实现
>
> 回归门禁会检测 `style=` 并失败。

### 6.2 转义统一

`app-render.js` 中所有属性插值必须统一转义，包括 `data-*`、`value`、`placeholder`。
使用 `escapeHtml()`（来自 `app-utils.js`），不要漏掉任何一个插值点。

### 6.3 modulepreload 清单必须精确匹配

`index.html` 的 `modulepreload` 列表必须与 `src/**/*.js` 模块集合**完全一致**：

- 入口 URL 与 `<script>` 标签**逐字符相同**（含 `?v=` 版本戳）
- 依赖模块使用**无版本号** URL（保证 import URL、preload URL、SW URL 三者字节一致）
- 不能有缺失项，也不能有陈旧项

由 `scripts/validate-frontend-manifest.mjs` 校验。
> 注意：该校验**只针对 JS**，CSS 文件不参与此校验。

### 6.4 渲染层补丁机制

`app-actions.js` 的 `render()` 会在 `shellSignature()` 匹配时短路为 `patchCurrentPage()`：

- **同 tab、无浮层的纯数据变化** → 只重建当前页容器
- **结构性变化**（切 tab、开浮层、登录/引导分支）→ 走完整 `root.innerHTML = appShell()`
- 补丁内还会用 `runtime.lastPageHtml` 做基线比对；若页面 HTML 未变则完全跳过重建
- 重建时会捕获并恢复聚焦控件（含光标位置），避免打断用户输入

> ⚠️ 修改渲染层时注意：**只改 CSS 通常不需要动渲染层**。
> 若确实要改 DOM 结构，需同步评估 `shellSignature()` 是否要纳入新状态。

### 6.5 静态文件服务用异步 IO

必须使用 `fs.promises.stat`，避免高并发下阻塞事件循环。

### 6.6 压缩与 ETag

- Brotli 使用 `params[BROTLI_PARAM_QUALITY]`；仅当 `Accept-Encoding` 含 `br` 且 q-value > 0 时优先于 gzip
- ETag 必须带 `-br` / `-gzip` 后缀以区分编码变体

### 6.7 安全优化优先级

项目约定：**安全优化优先于性能优化**，且第一批安全方案（转义统一 + HSTS）必须最先落地。

## 9. 给接手者的三条关键提醒

1. **验证实际加载的版本** — 改完运行 `npm run bump:version`，检查在线资源与离线重开。
   Android 还必须同步工程并重新构建 APK；单独生成 `dist-android` 不会更新已有 APK。

2. **接管旧变量 ≠ 完成改造** — 必须额外扫描并覆盖硬编码颜色值，
   否则会出现"底色变了但按钮还是绿的"这种半吊子状态（正是本次踩的坑）。

3. **优先在主题文件里覆盖，不要改旧 CSS** — 保持旧文件原样可以让改造可回滚，
   也避免污染原有代码。所有覆盖集中在一个文件里，便于审阅与后续调整。
